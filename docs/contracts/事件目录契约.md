# 事件目录契约

tomo 语义层的唯一事实源：**抽象事件目录** + **各 Agent 原生事件 → 抽象事件的映射** + **两条输出通道各自的默认事件层**。
本文档是主进程事件白名单、转发器/插件路由、渲染进程事件目录 UI、角色包（`.zip`）事件名、make-character 台词表事件节的共同依据。

- **代码事实源**：`src/shared/events.ts`（本契约的全部常量与纯函数）
- **消费方**：`electron/src/agent/*`（hook 装配）、`electron/src/event/*`（语音匹配）、`electron/src/pet/*` + `src/shared/pet-action.ts`（状态动作）、`src/lib/types.ts`（转出入口，渲染进程一律从它 import，不再有第二份目录）、tomo-create-charater 仓库的 `.claude/skills/make-character/*`（包生成）

---

## 一、分层原则

| 层 | 内容 | 谁定义 |
|----|------|--------|
| 原生事件层 | 各 Agent 官方 hook 事件的名字与 payload | 各家 Agent |
| **抽象事件层** | tomo 自己的 kebab-case 词表（16 个），Agent 无关 | tomo（本契约） |
| 通道事件层 | 语音通道 8 个（白名单）/ 宠物通道 16 个 | tomo（本契约 + [事件状态映射契约](事件状态映射契约.md)） |

抽象层存在的唯一理由：**两条输出通道对事件的需求不同**。语音是强打扰、由用户逐条绑定，只需要低频高价值的 8 个；宠物是弱打扰、无条件镜像 Agent 状态，需要全部 16 个。若不做抽象层，这个差异就只能靠「每接一个 Agent 就手工维护两套原生事件名」来表达，而各家 Agent 的原生词表既不重合也不稳定。

**三条护栏（违反即测试报错）**：

1. **抽象层只做分类学，不做策略**——它只回答「这个原生事件属于哪个语义类别」，不回答「该不该播语音」「该切什么动画」。策略分属两条通道各自的契约。
2. **同 Agent 内 native → abstract 必须单射**——一个原生事件只能映射到一个抽象事件（多对一允许：多个原生事件可归入同一抽象事件）。这条消灭了「同一事件两套解释」的歧义。
3. **写不进 hook 的原生事件 = 不存在**——不映射的原生事件不进 `NATIVE_TO_ABSTRACT`，因此结构上不可能出现在任何 Agent 的 hook 集里。事件集的裁剪（不收录哪些官方事件）由「不映射」表达，理由写在映射表的内联注释里。

## 二、抽象事件目录（16）

| 抽象事件 | 含义 | 覆盖 Agent |
|----------|------|-----------|
| `session-start` | 会话启动/恢复 | 全部 6 家 |
| `session-end` | 会话终止 | 除 opencode 外 5 家 |
| `prompt-submit` | 用户提交 prompt、本轮开始 | 除 opencode 外 5 家 |
| `post-tool-use` | 工具调用成功结束 | 全部 6 家 |
| `post-tool-use-failure` | 工具调用失败（回合未结束） | claude-code / cursor / kimi-code / copilot |
| `permission-request` | Agent 请求用户授权 | 除 cursor 外 5 家 |
| `turn-complete` | 一轮回复正常结束，Agent 交还控制权 | 全部 6 家 |
| `turn-failure` | 一轮回复因错误结束 | claude-code / kimi-code |
| `subagent-start` | 子代理启动 | claude-code / codex / cursor / kimi-code / copilot |
| `subagent-stop` | 子代理结束 | claude-code / codex / cursor / kimi-code / copilot |
| `pre-compact` | 上下文压缩前 | claude-code / codex / cursor / kimi-code / copilot |
| `post-compact` | 上下文压缩后 | claude-code / codex / opencode / kimi-code |
| `file-edited` | 文件被 Agent 编辑 | opencode / cursor |
| `task-created` | 待办任务创建 | claude-code |
| `task-completed` | 待办任务完成 | claude-code |
| `session-error` | 会话级错误 | opencode |

命名说明：
- `turn-complete` / `turn-failure` 刻意不叫 `stop` / `stop-failure`——「stop」是 Claude Code 家族的原生词，抽象层不应被单一家族的命名绑架，「一轮回复结束」才是语义。

> `session-error` 与 `turn-failure` 的状态动作相同（见 [事件状态映射契约](事件状态映射契约.md)），但语义层级不同：一个是会话级故障，一个是回合级失败。分开登记是为了让将来的策略分化（如会话级错误需要更醒目的提示）有落点，也为了不让 opencode 的错误事件被误归入「回合」这个它没有的概念。

**没有 `notification`**：语义太通用（等待输入/权限/空闲混杂），跨 Agent 无稳定对应，宁丢勿错。将来若要做，正确的落点是 matcher 维度（区分通知类型）而不是新抽象事件——记为 2.x 候选。

## 四、两条通道的默认事件层

| 层 | 常量 | 内容 | 谁消费 |
|----|------|------|--------|
| 语音层 | `VOICE_EVENTS`（8） | `session-start` `session-end` `prompt-submit` `turn-complete` `turn-failure` `permission-request` `post-tool-use-failure` `task-completed` | **可绑语音的白名单**：绑定页只列这 8 个；make-character 台词表的事件节；**包格式与市场上传的事件名校验** |
| 宠物层 | 全部 16 | 见 §二 | 状态机（见 [事件状态映射契约](事件状态映射契约.md)） |

**语音层选这 8 个的理由**：每会话/每轮最多触发一次、陪伴感强、音量上不会淹没用户。高频与内部事件（`post-tool-use` / `file-edited` / `task-created` / `subagent-*` / `pre-compact` / `post-compact` / `session-error`）刻意**不进这一层、也不可绑**——它们只是宠物状态的驱动源。

> **这是白名单，不是默认分组**（2026-09-20 收窄）：此前 16 个都能绑、8 个只是"默认摆在前面"，现在**只有这 8 个能绑**。连带三处：绑定页不再分组（扁平列 8 个）；包内 `manifest.events[].event` 必须是这 8 个之一（导入校验与市场服务端上传校验同源）；存量库里白名单外的绑定由 migration 3 删除。

**宠物层收全部 16 个**：视觉是弱打扰的无条件镜像，事件越多状态越准。不需要用户配置。

> 两层的**集合不同**，且性质也不同：语音层是**白名单**（能绑什么由它定死），宠物层是**无条件镜像**（不可配置）。

### HOOK_EVENTS 由两层反查得出

```ts
HOOK_EVENTS[agent] = reverse(NATIVE_TO_ABSTRACT[agent], VOICE_EVENTS ∪ PET_EVENTS)
```

即：**某 Agent 该装哪些 hook，是「两条通道需要什么」反查出来的结果，不是手写的清单**。因为宠物层已收全部 16 个，实际上每个 Agent 的 hook 集 = 它能映射的全部原生事件：

| Agent | hook 数 | 装的事件 |
|-------|--------|---------|
| claude-code | 14 | §三 Claude Code 表全部 |
| codex | 10 | §三 Codex 表全部 |
| opencode | 7 | §三 opencode 表全部 |
| cursor | 10 | §三 Cursor 表全部 |
| kimi-code | 12 | §三 Kimi Code 表全部 |
| copilot | 10 | §三 Copilot 表全部 |

由此得到一条重要性质：**hook 集与角色无关，是固定的**。角色只决定「这些事件里哪些有音频」，不影响装什么 hook——装配永不因用户绑定变更而重写。

## 五、路由协议（投递侧烘焙）

抽象层落在**投递侧**，不在信封里协商：

```text
Agent 原生事件（如 claude-code 的 "Stop"）
   │
   ▼ 转发器/插件内烘焙的 NATIVE_TO_ABSTRACT 查表
抽象事件（"turn-complete"）
   │ POST /event  { agent: "claude-code", event: "turn-complete", … }
   ▼
tomo Runtime —— 从此刻起全链路只认抽象名
```

- **转发器**（`tomo-forwarder.cjs`，安装时生成）：源码里烘焙 `NATIVE_TO_ABSTRACT[该 Agent]`，读 stdin 的 `hook_event_name` 后查表，**查不到直接 `process.exit(0)` 不投递**（未映射的原生事件根本不会打扰 Runtime）。
- **opencode 插件**：同理，`event.type` 查表后再转发（opencode 拿不到 argv，烘焙是唯一选项）。
- **映射不进 argv**：hook 命令行里只带 Agent id，不带事件名。原因是 Codex 的 hook 需要用户逐条信任，全部事件共用一个 command 意味着只需信任一次，且事件集增删不触发重新信任。
- **服务端校验**：`event` 必须 ∈ `ABSTRACT_EVENTS`，否则 422 + warn（旧版转发器投递原生名会被挡在这里，提示重装）。

## 六、维护纪律

### 加一个抽象事件
1. `src/shared/events.ts`：`ABSTRACT_EVENTS` 加名字 + `ABSTRACT_EVENT_META` 补 `label`/`description`（编译期类型收窄强制）
2. `PET_ACTION`（`src/shared/pet-action.ts`）补状态动作——**编译报错兜底**：`Record<AbstractEvent, StateAction>` 缺一个就不通过
3. 判断是否进 `VOICE_EVENTS`（进 = 用户可绑语音 + make-character 需补台词节）
4. `NATIVE_TO_ABSTRACT` 给各家补映射（哪家没有就哪家空着，缺口是显式事实，不是遗漏）

### 接一个新 Agent
1. 加 `AgentId` + `AGENT_META`
2. `NATIVE_TO_ABSTRACT` 加一段
3. 写适配器（`AgentAdapter`）+ 注册表登记

**不需要**动 `HOOK_EVENTS`（推导得出）、不需要动绑定页（它直接列 `VOICE_EVENTS`）、不需要动任何存量角色包。

### 护栏测试（`src/shared/events.test.ts`）
1. `NATIVE_TO_ABSTRACT` 每个 Agent 段内单射（值可以重复，键必须唯一——键本来就唯一，测的是「同一原生名不得出现在两段」之外的语义：**列出的原生名必须与官方事件名精确一致**，由各 Agent 的事件名清单常量断言）
2. `HOOK_EVENTS === reverse(NATIVE_TO_ABSTRACT, VOICE_EVENTS ∪ PET_EVENTS)`（推导式与常量不得漂移）
3. `VOICE_EVENTS ⊆ PET_EVENTS`
4. `PET_ACTION` 的键集 === `ABSTRACT_EVENTS`（无遗漏、无多余）
5. 每个 `ABSTRACT_EVENT_META` 的键 ∈ `ABSTRACT_EVENTS`
6. 每个 Agent 的 `HOOK_EVENTS` 非空且不含任何未映射的原生名
